# RFC — Custom QR Code Studio (1stdev.link)

Status: PROPOSED / DESIGN & IMPLEMENTATION PLAN ONLY  
Audit base: main commit df822e272db60feb273ed38495bc10e41de96c21 (2026-11-09)  
Audience: product, design, React/Vite, Cloudflare Workers, D1/R2/KV, QA, security  
**This RFC does not add features, modify a database, or deploy production.**

## 1. Product goal and user promise

**"Desain QR sesuai brand, tetap mudah dipindai, dan dapat dikelola dari satu tempat."**

Build a custom QR feature that serves:
- Creator: portfolio and bio page QR for business cards, stickers, media kits.
- UMKM: menu/catalog/WhatsApp or storefront links on packaging and tables.
- Affiliate: branded QR to an existing shortlink, with accurate referral destination.
- Event/community: poster QR with label and optional campaign attribution.

Three different deliverables must not be confused:
1. **Visual QR (P1):** QR containing the actual existing bio URL or shortlink. Free, no new D1 tables. The PNG/SVG is static; styling can be edited before export. Existing shortlink can change its destination when the API supports that.
2. **Saved QR design (P2):** QR design and logo references persist in the authenticated user's D1 records; editing a *design* does not alter a previously printed static QR. D1 migration and authenticated APIs needed.
3. **Dynamic QR (P3):** QR encodes a stable ID such as \`https://1stdev.link/q/Q8aB... \` (no trailing blank). The Worker resolves to a linked shortlink's current destination or to a user's current public profile. A printed QR remains valid after editing a target or changing profile handle, provided the QR and target remain active. D1 + Worker route needed.
4. **QR opens analytics (P4):** Aggregate non-bot requests to that QR redirect route. Call these *QR opens* or *QR link visits*, **not** camera scans, unique visitors, sales, or conversions.

## 3. IA / entry points

Keep top-level navigation unchanged: **Beranda, Halaman, Link, Statistik, Pengaturan**.

- **Link → QR Studio:** segmented subview \`Semua Link | QR Studio\` inside the existing Links destination. Does not alter currentTab/hash semantics.
- **LinkCard → QR Code:** per-link contextual action opens editor pre-selected for that link. Disabled for content-only/nonredirectable blocks.
- **ShareSheet → Custom QR:** clear button beside current default QR; opens designer pre-filled with public profile \`/@handle\`.
- **Beranda → Quick Action:** optional \`Buat QR\` uses editor with profile preselected, preferably after first feature release.
- **Saved QR Gallery (P2):** search, filter by target/profile/link, card preview, modify, duplicate, download, archive, delete. Support empty/error/loading.
- **QR analytics (P4):** a QR detail pane; optionally aggregate entry in existing Statistik dashboard with accurate labeling.

Do not expose an unprotected public QR design-editing page.

## 4. Primary UX flows

### A. Instant custom QR (no new DB)

1. Tap \`Bagikan halaman\` or \`QR Code\` on a shortlink.
2. \`QRStudioSheet\` opens with selected destination and default safe QR.
3. User chooses preset, foreground/background colors, dot/corner shape, optional permitted logo.
4. Preview updates in a debounced async renderer. Status: \`Membuat pratinjau\` → \`Siap dipindai\` or \`Perlu diperbaiki\`.
5. Decode-validation runs against exact payload. Invalid style automatically blocks download (with clear explanation and \`Gunakan desain aman\` button).
6. Export PNG 512/1024/2048 px, self-contained SVG. Files use safe slugs and are generated client-side.
7. User returns to Share/Links. This temporary design is not automatically a saved QR.

### B. Saved design (requires claimed account and P2)

1. Same editor; user chooses \`Simpan desain\`, provides title.
2. Guest is invited to Save Account first while preserving design in memory until auth completes. Download remains available for guests.
3. POST \`/api/qr\` or PATCH \`/api/qr/:id\`, optimistic status with explicit success/failure and retry.
4. Gallery shows last modified time, type, status and download/edit/duplicate/delete.
5. User can edit *appearance* while preserving QR destination and public QR ID.
6. On delete, confirm impact; dynamic route is deactivated/tombstoned. Already printed QR must not silently redirect elsewhere.

### C. Dynamic profile/shortlink QR (P3)

1. Choose a real \`profile\` or owned, redirectable \`link\` as target.
2. Save Dynamic QR, receive permanent \`/q/:publicId\` URI to encode.
3. Worker resolves target by user ownership relation, profile handle or link destination.
4. If profile handle or link destination changes, the QR code does NOT change.
5. On inactive/deleted QR, show clear unavailable result; never reuse IDs. On inactive/deleted linked shortlink, QR is unavailable unless target is updated.
6. On QR open, count one qualified QR entry and, for link target, at most one matching link click, with shared redirect logic (not two chained analytics hits).

### D. Analytics (P4)

- Summary: QR opens, date series 7/30 days, country distribution and top QR designs.
- Link clicks remain a separate existing metric. Display a short disclosure: opening the camera without opening the URL is NOT observed.
- Do not claim unique visitor or scan-to-conversion rates without a separate consent/privacy-approved model.

### E. Error / empty scenarios

- Invalid URL, disabled/deleted link, image upload denied for guest, oversized logo, insufficient contrast, failed decode, offline, failed save, slow phone, export error, expired/missing QR ID, and browser downloads unsupported.
- Never lose current designer settings when network fails or user changes tabs in the editor; give unsaved changes warning when closing if relevant.

## 6. QR design / format contract

Proposed TS data shape:

\`\`\`ts
type QrTarget =
  | { type: 'profile'; userId: string }
  | { type: 'link'; linkId: string };

type QrDesignV1 = {
  version: 1;
  preset: 'classic' | 'brand' | 'minimal' | 'rounded' | 'business' | 'event';
  dots: 'square' | 'rounded' | 'dots';
  corners: 'square' | 'rounded' | 'extra-rounded';
  foreground: string; // 6-digit #RRGGBB, validated
  background: string; // solid #RRGGBB, validated
  cornerColor?: string;
  errorCorrection: 'Q' | 'H'; // internally derived for logo safety
  quietZoneModules: 4; // non-editable minimum
  logoKey?: string;     // owner-scoped R2 image, never arbitrary external SVG
  logoScale?: number;   // clamped, proposed max ~0.18 QR width
  frame?: 'none' | 'simple' | 'label';
  frameText?: string;   // visible caption outside quiet zone, bounded and escaped
};
\`\`\`

**Never store raw HTML, unsafe SVG or user-supplied CSS in design_json.** Use allowlisted types and numeric/color constraints on both client and server. Persist only validated versioned JSON and trusted media keys.

Default QR generator:
- Quick/basic: keep existing \`qrcode\`.
- For rounded/dot patterns and corner variants: evaluate lazy-loaded \`qr-code-styling\` in a proof-of-concept, pin exact reviewed version after security/license/bundle inspection.
- Use \`@zxing/browser\` or equivalent for client and CI decode checks; verify real physical scans too.
- Generate SVG exports with embedded/sanitized images only; reject remote image links or \`<script>\`, \`foreignObject\`, event handlers and external references.

## 7. Scannability and export rules (release-blocking)

1. **Quiet zone:** at least four QR modules of clear margin around the code. Current ShareSheet's \`margin: 2\` must not be inherited as the new printed export default. Protect the margin even inside a decorative frame.
2. Contrast heuristic for foreground/background: propose >=4.5:1 with solid, opaque light background, plus **actual decode test**. This threshold is a product-level heuristic, not a QR standard.
3. For no logo use \`Q\` error correction by default; for logo use \`H\` as a starting point. H is not a guarantee that all center-logo sizes will decode.
4. Center logo: propose maximum 18% of QR *side length* as first guardrail, with solid light backing, bounded white margin, no finder occlusion, and repeated decode tests. Lower further if necessary.
5. Disable/avoid low-contrast gradients in MVP. Add only after tests with multiple combinations and print samples.
6. Export format: \`PNG\` with 512 / 1024 / 2048 pixels; \`SVG\` with self-contained image and outer caption. Keep meaningful filenames, e.g. \`1stdev-qr-catalog-20261109.png\`.
7. Decode the **final composited export** (including logo and frame), not only the black-white underlying matrix. Test at 256/512/1024 raster dimensions and on real phones. If any required condition fails: block export and explain why, allow \`Reset to safe design\`.
8. Preserve decoded URL byte-for-byte; reject javascript:/data:/file: schemes, private/loopback redirects and invalid owned link IDs.
9. Printed QR quality depends on real print resolution and code density; do not promise a universal printable physical size. Test agreed 25–40mm samples, matte/gloss and camera distance as part of print QA.

Sources/reference: DENSO WAVE official QR margin/error correction docs; \`qr-code-styling\` browser renderer/API; \`@zxing/browser\` image decode.

## 8. Persistence architecture

### P1: no schema changes

Frontend state:
- \`selectedTarget\`, \`design\`, \`previewRenderId\`, \`validationStatus\`, \`exportStatus\`.
- Optional session-local draft in memory, not cross-user localStorage leakage.
- The QR encodes \`https://1stdev.link/@handle\` or \`https://1stdev.link/:slug\`.
- Existing redirect and link analytics continue; **cannot** attribute shortlink clicks exclusively to QR.

### P2: migration 0004_qr_codes.sql (proposal; create only with implementation PR)

\`\`\`sql
CREATE TABLE qr_codes (
  id TEXT PRIMARY KEY,
  public_id TEXT NOT NULL UNIQUE,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  target_type TEXT NOT NULL CHECK(target_type IN ('profile','link')),
  link_id TEXT REFERENCES links(id) ON DELETE SET NULL,
  design_json TEXT NOT NULL,
  logo_key TEXT,
  is_active INTEGER NOT NULL DEFAULT 1 CHECK(is_active IN (0,1)),
  created_at INTEGER NOT NULL DEFAULT (unixepoch()),
  updated_at INTEGER NOT NULL DEFAULT (unixepoch())
);
CREATE INDEX idx_qr_codes_user_updated ON qr_codes(user_id, updated_at DESC);
CREATE INDEX idx_qr_codes_link ON qr_codes(link_id);
\`\`\`

- \`public_id\` random unguessable fixed-length URL-safe string (e.g. 14+ chars); never reuse on deletion.
- \`target_type=profile\` resolves by \`qr_codes.user_id\` to current profile handle, avoiding stale QR if user renames handle.
- \`target_type=link\` must verify link belongs to same user and is redirectable when created/edited. If \`link_id\` becomes NULL after deleting a link, dynamic QR becomes unavailable (not arbitrarily retargeted).
- Suggested initial user quota: 50 saved QR records/account, enforced in Worker with D1 transaction or trigger to avoid races. This is a **proposed product quota**, not an existing plan limit.
- Static file render can be generated client-side and need not store PNG/SVG on R2. Store only design_json and logo_key; reproducibility requires pinning renderer version/design schema.
- Guest: allow design/download but require account claiming before saving and R2 image upload.

### P4: migration 0005_qr_visits_daily.sql (proposal)

\`\`\`sql
CREATE TABLE qr_visits_daily (
  qr_id TEXT NOT NULL REFERENCES qr_codes(id) ON DELETE CASCADE,
  date TEXT NOT NULL,
  country TEXT NOT NULL DEFAULT 'XX',
  opens INTEGER NOT NULL DEFAULT 0 CHECK(opens >= 0),
  PRIMARY KEY(qr_id, date, country)
);
CREATE INDEX idx_qr_visits_by_day ON qr_visits_daily(date);
\`\`\`

- Aggregates only; do not persist raw IP address or per-scan profile.
- Update with atomic \`INSERT ... ON CONFLICT DO UPDATE\` in Worker waitUntil, following existing link analytics pattern.
- Cache counters for UI if necessary; do not add per-request D1 writes beyond existing budget without load tests.

### Assets

- Extend \`POST /api/media/:type\` with explicit \`qr_logo\` target and owner-scoped prefix, only on authenticated claimed accounts.
- Accept MIME-sniffed PNG/JPEG/WebP only (reuse existing validation); proposed max 512KB after resizing. Reject SVG upload.
- Image hash, dimensions and ownership validated; logo deleted using safe cleanup after references are gone. Do not leak another user's R2 object key in QR design APIs.

### Authenticated design endpoints (P2)

Example success (201):
\`\`\`json
{
  "status": "success",
  "data": {
    "id": "qr_internal_uuid",
    "public_id": "Q8ab92d3pKx72t",
    "qr_url": "https://1stdev.link/q/Q8ab92d3pKx72t",
    "title": "QR Katalog Toko",
    "is_active": 1,
    "updated_at": 1794182400
  }
}
\`\`\`

Target owner and all write permissions checked server-side; do not trust \`user_id\` from request. Return meaningful codes:
- 400 invalid style/title/type; 401 not authenticated; 403 guest cannot persist/upload or foreign logo; 404 not owned; 409 concurrent revision/duplicate; 413 oversized; 422 unsafe URL/unscannable export; 429 rate/quotas; 503 D1/R2 unavailable.
- Optimistic UI should use \`updated_at\` or explicit revision for concurrent editing; never overwrite a newer saved design blindly.
- No SVG processing required in Worker to save QR design, reducing attack surface.

### Public redirect route (P3)

\`GET /q/:publicId\`:
1. Match before generic \`/:slug\` route. Add \`q\` to \`RESERVED_SLUGS\`; review conflicts with any pre-existing shortlink slug exactly \`q\` before production change.
2. Reject malformed IDs; look up qr_codes by unique public_id.
3. Verify active, owner still exists, and target link/profile is valid.
4. Resolve to current profile \`/@handle\` or existing owned redirectable link destination. Keep smart iOS/Android routing for linked shortlinks by reusing a shared redirect service, **not** naive independent logic.
5. Return 302 redirect (or 404/410 for revoked or missing target); \`Cache-Control: no-store\` on status that can change, avoid stale negative caches and 24h invalidation surprises.
6. Count one qualified QR open; for linked QR, increment existing link click once as well without making a two-hop redirect via \`/:slug\`.
7. Do not fetch or render external user URL from Worker; only redirect after existing URL validation and anti-abuse checks.

Deletion policy: QR IDs must not be recycled. For previously printed/disabled QR, a simple descriptive unavailable page or 410 status may be friendlier than a silent 404, but avoid exposing private owner metadata.

### Analytics endpoint (P4)

- GET \`/api/qr/:id/analytics?range=7d|30d\`; must prove ownership.
- GET \`/api/qr/analytics/summary?range=7d|30d\` for card aggregates if needed.
- Response: \`total_opens\`, \`by_date\`, \`by_country\`; optional top QR ranking.
- Do not label counts as camera scans, deduplicated people or conversions.

## 11. Security, privacy and abuse

- Profile or link selectors list only items belonging to current user; no arbitrary cross-user QR targets.
- Raw arbitrary URL QR in MVP? **Not supported**: require user to create an owned shortlink first, preserving existing validation/abuse quotas. A static external URL tool is optional later with separate review.
- Reject javascript:, data:, file:, credentials in URL, localhost/private addresses, malformed ID, content-only links.
- Rate-limit design create/update, logo uploads, and redirect route abuse. Keep existing bot filtering and label metric appropriately.
- Do not store individual IPs, precise scan GPS, device fingerprints or cross-site marketing cookies.
- R2 logo image ownership is essential: a client-supplied logo_key must belong to the same user.
- Downloaded SVG must be self-contained and sanitized. No user-provided SVG blobs or remote references.
- If link URL can be changed later, show QR destination preview and warn users about phishing risk; moderate/disable abuse with existing link controls.
- Display filename/frame text as plain text only; avoid injecting arbitrary SVG markup.
- Privacy disclosure for QR metrics: only daily aggregated counts and approximate country via Cloudflare headers.
- Security review against open redirect via inconsistent QR and shortlink validators.

## 12. Accessibility & internationalization

- All controls keyboard-operable; visible focus, 44px-ish touch targets, accessible radio groups or \`aria-pressed\` preset buttons.
- Color has a hex text input and accessible label; never communicate validity only by green/red.
- Screen reader status \`role=status\`: generating, validated, saved, failed.
- QR preview image alt text describes destination and state, not an unhelpful "QR".
- Maintain ID + EN copy for all settings and toast/error states.
- Reduced-motion and offline/retry states.
- Mobile sticky footer not overlapped by app's bottom dock, keyboard or safe-area.

## 13. QA matrix and acceptance criteria

### Browser/device matrix

- Responsive: 320, 360, 390, 768, 1024, 1280, 1440, 1920px; 200% zoom.
- Chromium CI all PRs; WebKit/iOS Safari and Android Chrome before release.
- Real scanning: at least two distinct phones/camera apps, on-screen bright/dark and printed samples; test deliberately poor color/logo combinations reject.
- Test formats: SVG embedded logo, PNG @512/1024/2048, download filename/MIME, no CORS-tainted canvas, offline failure.
- Test each target kind: profile, owned active shortlink, disabled shortlink, deleted shortlink, missing profile, long URL.
- Test presets all six with logo/no logo, rounded/square dots, i18n, long text, tiny viewport.
- P2 test guest save denied with draft preserved, claimed save/refresh/edit/duplicate/delete, owner isolation, quota and concurrent edits.
- P3 test stable \`/q/:publicId\` after handle rename, link destination edit, link inactive/deleted, key exhaustion, cache behavior, query keys, bot filtering and smart device URLs.
- P4 test aggregate counts by date/country, no fake unique scans, double-count prevention, deleted QR effects.

### Acceptance thresholds

- 100% required presets decode their exact payload in automated rasterized image tests at target sizes, plus manual physical scans before launch.
- A known-invalid combination blocks export with clear recovery; never download a knowingly invalid QR.
- No overflow or clipped action at any target viewport.
- Fast preview re-renders are debounced/cancelled to prevent stale design flashes; controls responsive on reference lower-end mobile devices.
- Correct PNG/SVG download and file contents; no broken cross-origin logo.
- No new main-nav destination and no regression to existing ShareSheet links/WhatsApp/copy.
- Strong API ownership tests, no untrusted logo refs, and no unsafe redirect targets.
- Existing build + Worker tests + browser QA remain green.
- Measured performance budgets and bundle size are recorded before declaring "fast"; don't claim measured results in advance.

## 15. Cloudflare deployment and rollback

### Preview and staging

1. Each frontend PR: GitHub Verify EdgeLink + UI Browser QA + Cloudflare Pages branch preview. Use local mock data and no production mutations.
2. QR-04 migrations: new numbered migration \`0004_qr_codes.sql\` only in isolated staging D1 first, with backup/snapshot strategy and owner isolation tests.
3. QR-05 Worker route changes must be tested on staging Worker with separate D1/KV/R2 bindings. Verify \`/q/:publicId\` vs \`/:slug\`, \`/@handle\`, API, bot handling.
4. QR-06 migration \`0005_qr_visits_daily.sql\` and metrics must be tested under realistic redirect request load.

### Production order

- For visual-only QR-01..QR-03, merge main → Cloudflare Pages deploy → confirm commit SHA, HTML/JS/CSS assets, QR downloadable/decodable.
- For QR-04+, apply additive D1 migrations **before deploying Worker API requiring those tables**. Preserve previous Worker functionality when feature flag off.
- Deploy Worker separately with expected bindings; verify existing shortlink and bio traffic, then enable new QR API/routes after smoke.
- Deploy Pages frontend that calls new API only after Worker/API is ready; canary/flag where practical.
- Inspect Cloudflare Pages production, Worker endpoints and custom \`1stdev.link\` separately. Automated domain 403 may be a WAF challenge and must be validated via real browser/security events, not assumed to be a frontend failure.
- Save production version/rollback references and measure 4xx/5xx, preview errors, redirect errors, D1 analytics writes.

### Rollback

- QR-01..03: restore previous Pages release; no schema changes.
- QR-04+: revert Worker/frontend while **retaining additive D1 columns/tables**; do not auto-drop schema or delete saved QR records.
- QR-05: preserve printed \`/q/:publicId\` validity after any rollback. Prefer a Worker compatibility handler over removing public QR routes.
- Don't reuse public IDs or issue new URLs to the same QR without an explicit migration plan.

## 16. Product decisions to approve before implementation

1. **Nav:** QR Studio is a Links subview + per-link action + ShareSheet shortcut, not sixth global tab.
2. **Target set:** MVP profile and owned existing shortlinks only; no arbitrary raw external URLs.
3. **Guest policy:** can customize and download; must claim account to save designs and upload logo.
4. **Style guardrails:** quiet zone 4 modules, solid background, high contrast, logo limited and decode-validated.
5. **Exports:** PNG 512/1024/2048 and SVG; PDF not in MVP.
6. **Storage:** versioned design JSON in D1, image logo in existing R2 (P2).
7. **Dynamic path:** \`/q/:publicId\` owned by the Worker, not a long external redirect chain.
8. **Metrics terminology:** "Pembukaan QR"/"QR opens", not physical scans or unique people.
9. **Release strategy:** split client-only feature from saved/dynamic/analytics phases. No surprise D1/Worker modifications during visual PR.
10. **Library:** prefer existing qrcode for baseline; evaluate qr-code-styling for advanced shape UX and ZXing decoder for acceptance tests.
